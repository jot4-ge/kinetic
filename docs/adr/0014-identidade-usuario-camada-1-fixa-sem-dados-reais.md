# Identidade de Usuário na Camada 1 é fixa e sem dados pessoais reais

O onboarding (primeira tela de produto) precisa criar um Usuário e um Plano e, nas aberturas seguintes, decidir se manda a pessoa para `/onboarding` ou `/hoje`. Isso levantou duas perguntas de identidade que o domínio não respondia sozinho: **qual é o id do Usuário** (o `UsuarioRepositorio` só expõe `buscar(id)` — não há `listar`, então a aplicação precisa saber o id de antemão) e **quais dados pessoais coletar**, já que `usuarioSchema` (Zod) exige `nome` (não-vazio) e `email` (formato válido) — validados na leitura, não na escrita.

Decidimos, para a Camada 1:

**(a) Um id fixo, `ID_USUARIO_LOCAL = "usuario-local"`, em vez de um UUID gerado + ponteiro em `localStorage`.** A Camada 1 é single-user por contrato — o `UsuarioRepositorio` foi desenhado só para get-by-id (ver `contratos.ts`), sem varredura. Um id fixo é recuperável sempre e sobrevive à limpeza de `localStorage`; um UUID gerado exigiria persistir "qual é o id atual" em algum lugar fora do IndexedDB, e se esse ponteiro se perdesse o registro do Usuário ficaria órfão (irrecuperável sem um `listar` que o repositório deliberadamente não tem). Os **Planos continuam com UUID gerado** por serem múltiplos por Usuário ao longo do tempo (um Ativo + Arquivados, ADR-0002) — só a identidade do Usuário é fixa.

**(b) `nome` e `email` não são coletados nesta fase, mesmo o schema exigindo os dois.** O onboarding preenche placeholders fixos: `nome: "Você"` e `email: "usuario@exemplo.invalid"`. O `.invalid` é um TLD reservado pela RFC 2606, garantidamente não-roteável — sinaliza inequivocamente que não é um endereço real, nunca é confundível com o e-mail de uma pessoa, e ainda assim passa a validação de formato do Zod. A Camada 2 substitui esses placeholders por identidade real.

**(c) Rejeitamos coletar `nome`/`e-mail` reais no onboarding.** Nenhuma tela desta fase (onboarding, tela "hoje", registro de aderência) precisa dessa informação para funcionar — as metas do Plano derivam apenas de biometria + objetivo. Coletar dado pessoal que não será usado, só para satisfazer campos do schema, é pior do que não coletar: cria uma superfície de dado sensível sem contrapartida de valor. Os campos permanecem no domínio (o schema não muda) porque a Camada 2 vai preenchê-los de verdade; nesta fase eles ficam com placeholders explícitos.

Esta decisão **não conflita com ADR-0004** (autoria separada de posse): `autor_id` e `usuario_id` continuam existindo como campos distintos e, na Camada 1, ambos apontam para o mesmo `ID_USUARIO_LOCAL`. A separação de autoria e a identidade real por usuário só se tornam necessárias na Camada 2, quando um Treinador/Nutricionista precisar criar/editar Planos de outros Usuários — momento em que o id fixo e os placeholders dão lugar a identidade real.
